# Decision log — the 2.1.0 polish track

One file per track (not per PR): every judgment call made while executing
the roadmap tail gets a dated entry here, so review of the batch PR can
challenge the calls, not discover them.

Format: **decision** — reasoning — (alternative rejected).

---

## D0. 2026-09-20 — process decisions for this track

- **One branch, one commit per step, one batch PR at the end** (`feat/2.1.0-polish-track`).
  The repo's culture is PR-per-feature, but seven sequential PR+CI+merge
  cycles for S/M items that all touch the same files (render path, budget
  headroom) spends the reviewer's attention on merge mechanics instead of
  the changes. Per-step commits keep the history bisectable; the batch PR
  keeps the conversation in one place. (Rejected: seven PRs — churn;
  one squashed commit — loses the per-step review units the user asked
  for: "one by one commit".)
- **Per-step review = tests + a rendered-page visual pass.** After each
  step the chart is driven through its changed behavior in a real browser
  (Playwright), screenshotted, and the screenshots are inspected by the
  visual judge agent before moving on. (This is the "review by ocr"
  instruction: machine review of rendered output, not of the diff.)
- **Version target 2.1.0**, CHANGELOG accumulates under Unreleased; the
  release itself is offered at the end, not assumed — cutting a release
  publishes to npm and is the maintainer's call to time.
- **Size budget:** the 66 KB ceiling has ~5.7 KB headroom at branch point
  (60.3 KB entry). Steps must fit inside it; if one can't, the budget
  raise is its own commit with the why (the standing rule).

## D1. 2026-09-20 — Step 1: y-range settle (the vertical twin of PR #78)

- **Policy: expand-now / contract-after-750ms-hold-under-90%-usage /
  snap-on-input-change.** A live feed must never clip (expansion is
  immediate, violated side only), but a per-render tight re-fit breathes:
  overlays track the forming close both ways and every new bar slides the
  window. Contraction requires the data to occupy under 90% of the
  settled width *continuously* for 750ms — a frame back above 90% resets
  the hold (this exact hole was caught by the oscillation unit test:
  without the reset, a returning old candidate adopts instantly off a
  stale timestamp). (Rejected: continuous re-fit — that IS the bug;
  animation/lerp toward target — needs a persistent RAF loop the
  render-on-demand design doesn't have.)
- **Snaps: pan (drag/wheel/trackpad), zoom (wheel/pinch/±keys), Home/End,
  fit()/dblclick, setVisibleRange, and the scale-input attributes
  (type/log/indicators/overlays) + bulk data (setData/clearData).**
  Deliberately NOT snapped: the auto-follow rightIndex write in `_render`
  and the loadMore prepend anchor — both are the live/streaming path the
  settle exists to smooth. (Judgment: mid-drag re-fitting is fine —
  jitter while the user's hand is on the chart reads as response, not
  shake; the complaint was passive viewing.)
- **The snap is an inlined field write (`this._ySettle = this._yNarrow =
  null`), not a `_snapY()` method.** Seven existing test files borrow
  prototype methods onto duck-typed stubs; a new `this._snapY()` call
  inside borrowed methods broke 15 of them until every stub grew the
  seam. A plain property assignment works on any stub and costs nothing.
  (Rejected: patching all stubs — churn now and for every future stub.)
- **Pane scales (volume etc.) are NOT settled** — only the main pane.
  Pane series oscillate too, but the visual weight of the main pane is
  the complaint; pane scales can inherit the same policy later if anyone
  notices. (Rejected: settling panes now — more state for no reported
  symptom.)
- **Review-method fallback (process):** the visual judge agent cannot
  read local files in this environment (it receives a CDN-upload
  confirmation instead of pixels), so the per-step visual review runs
  through the CDN-hosted image analysis instead, and every *quantitative*
  claim is additionally verified in-page (geometry/scale reads via
  `page.evaluate`) before a visual flag is acted on. Concretely this
  step: the judge flagged "right-edge candle clipping" — in-page geometry
  disproved it (last body edge x=799.1 vs separator x=848, 49px clear);
  a "clipped bottom bar wall" flag traced to the capture script's
  constant-volume synthetic data, not the renderer. Browser measurement:
  the rendered scale changed **once** across 40 oscillating ticks (was:
  every tick).
