# Decision log — the 2.1.0 polish track

One file per track (not per PR): every judgment call made while executing
the roadmap tail gets a dated entry here, so review of the batch PR can
challenge the calls, not discover them.

Format: **decision** — reasoning — (alternative rejected).

---

## D0. 2026-09-20 — process decisions for this track

- **One branch, one commit per step, one batch PR at the end** (`feat/2.1.0-polish-track`).
  The repo's culture is PR-per-feature, but seven sequential PR+CI+merge
  cycles for S/M items that all touch the same files (render path, budget
  headroom) spends the reviewer's attention on merge mechanics instead of
  the changes. Per-step commits keep the history bisectable; the batch PR
  keeps the conversation in one place. (Rejected: seven PRs — churn;
  one squashed commit — loses the per-step review units the user asked
  for: "one by one commit".)
- **Per-step review = tests + a rendered-page visual pass.** After each
  step the chart is driven through its changed behavior in a real browser
  (Playwright), screenshotted, and the screenshots are inspected by the
  visual judge agent before moving on. (This is the "review by ocr"
  instruction: machine review of rendered output, not of the diff.)
- **Version target 2.1.0**, CHANGELOG accumulates under Unreleased; the
  release itself is offered at the end, not assumed — cutting a release
  publishes to npm and is the maintainer's call to time.
- **Size budget:** the 66 KB ceiling has ~5.7 KB headroom at branch point
  (60.3 KB entry). Steps must fit inside it; if one can't, the budget
  raise is its own commit with the why (the standing rule).

## D1. 2026-09-20 — Step 1: y-range settle (the vertical twin of PR #78)

- **Policy: expand-now / contract-after-750ms-hold-under-90%-usage /
  snap-on-input-change.** A live feed must never clip (expansion is
  immediate, violated side only), but a per-render tight re-fit breathes:
  overlays track the forming close both ways and every new bar slides the
  window. Contraction requires the data to occupy under 90% of the
  settled width *continuously* for 750ms — a frame back above 90% resets
  the hold (this exact hole was caught by the oscillation unit test:
  without the reset, a returning old candidate adopts instantly off a
  stale timestamp). (Rejected: continuous re-fit — that IS the bug;
  animation/lerp toward target — needs a persistent RAF loop the
  render-on-demand design doesn't have.)
- **Snaps: pan (drag/wheel/trackpad), zoom (wheel/pinch/±keys), Home/End,
  fit()/dblclick, setVisibleRange, and the scale-input attributes
  (type/log/indicators/overlays) + bulk data (setData/clearData).**
  Deliberately NOT snapped: the auto-follow rightIndex write in `_render`
  and the loadMore prepend anchor — both are the live/streaming path the
  settle exists to smooth. (Judgment: mid-drag re-fitting is fine —
  jitter while the user's hand is on the chart reads as response, not
  shake; the complaint was passive viewing.)
- **The snap is an inlined field write (`this._ySettle = this._yNarrow =
  null`), not a `_snapY()` method.** Seven existing test files borrow
  prototype methods onto duck-typed stubs; a new `this._snapY()` call
  inside borrowed methods broke 15 of them until every stub grew the
  seam. A plain property assignment works on any stub and costs nothing.
  (Rejected: patching all stubs — churn now and for every future stub.)
- **Pane scales (volume etc.) are NOT settled** — only the main pane.
  Pane series oscillate too, but the visual weight of the main pane is
  the complaint; pane scales can inherit the same policy later if anyone
  notices. (Rejected: settling panes now — more state for no reported
  symptom.)
- **Review-method fallback (process):** the visual judge agent cannot
  read local files in this environment (it receives a CDN-upload
  confirmation instead of pixels), so the per-step visual review runs
  through the CDN-hosted image analysis instead, and every *quantitative*
  claim is additionally verified in-page (geometry/scale reads via
  `page.evaluate`) before a visual flag is acted on. Concretely this
  step: the judge flagged "right-edge candle clipping" — in-page geometry
  disproved it (last body edge x=799.1 vs separator x=848, 49px clear);
  a "clipped bottom bar wall" flag traced to the capture script's
  constant-volume synthetic data, not the renderer. Browser measurement:
  the rendered scale changed **once** across 40 oscillating ticks (was:
  every tick).

## D2. 2026-09-20 — Step 2: the offscreen hover layer

- **Second canvas (`canvas.ov`) stacked over the main one; the crosshair
  block moved out of `_render` into `_drawCrosshair(ctx)`.** `_hoverAt`
  (pointermove — the hottest path in the component) now refreshes the
  legend DOM and repaints only the overlay: browser-measured **0 full
  renders across 20 `_hoverAt` calls, 20 overlay paints**; e2e pins it
  (12 real mouse moves → `_render` count 0). `_render` ends with
  `_paintOverlay()` so a live tick refreshes the crosshair against the
  new scale instead of floating over a stale grid.
- **Only the crosshair moved.** Measure tool, brush band, positions and
  plugin layers stay on the main canvas — they ride full renders anyway
  (gestures/edits), and moving them buys nothing. (Rejected: moving
  pills/measure too — more surface, same renders.)
- **`exportPNG()` composites main + overlay** so an export taken while
  hovering keeps the crosshair exactly as before. Report export renders
  its own canvas — unaffected.
- **e2e helpers now composite every canvas in the shadow root** (what the
  eye sees, not the bottom sheet). Without this, the hover pixel-diff
  tests would silently stop seeing the crosshair. The `pr31` layers test
  needed two maintenance edits: `_updateLegend`/`_paintOverlay` stubs on
  its duck-typed chart, and its source-order assertion re-anchored
  (`_paintOverlay()` after `_drawLayers` — the crosshair block it used to
  grep for left the main render pass; ordering semantics unchanged).
- **Visual-baseline note:** zero baseline churn — the overlay draws the
  same commands at the same pixels, and specs screenshot the page, which
  composites naturally. Full e2e 66 passed.
- **Review note:** the full-page screenshot pass claimed "no crosshair";
  in-page pixel counting (2643 inked pixels on the overlay, vertical line
  at the expected x) and a zoomed-crop analysis (both dashed lines, both
  pills, intact candles — all confirmed) overruled it. The fixture's dark
  page margin around the 900px chart box fooled the model into reading
  missing chart area.

## D3. 2026-09-20 — Step 3: min/max downsampling — found mostly shipped, closed the line-chart gap

- **Investigation first: `buildColumns` (core.js) already IS min/max
  downsampling per pixel column** for the candle path — each column keeps
  max(high)/min(low), first open, last close, summed volume (shipped with
  the deep-zoom aggregation years of PRs ago; pr8 tests pin it). The
  roadmap line item was stale, not missing.
- **The genuine gap: line/area charts at deep zoom plotted one point per
  column (the last close), so a one-bar spike inside a pixel column was
  invisible.** `buildColumns` now also tracks `cMin`/`cMax` (close
  extremes); the line/area path emits both per column, nearest-to-previous
  first (the standard trick — no fake sawtooth inversions); `_mainScale`'s
  line-mode column scan uses the close extremes so the spike also drives
  the autoscale. Candles unchanged. (Rejected: emitting low/high instead
  of close extremes for lines — a line chart tracks closes; wicks aren't
  the series.)
- **Overlay indicator lines at deep zoom still sample per column** via
  `s[c.i1]` — intracolumn extremes of an SMA/EMA are sub-percentage noise;
  not worth the bytes. Documented here rather than fixed.
- **e2e:** new `downsample.spec.mjs` — 4000 bars, one close +40 mid-
  history, full-range zoom → asserts the aggregated path is active
  (spacing < 0.7), the settled scale includes the spike, and the accent
  stroke passes within 12 device px of the spike's exact (x, y). Two
  test-harness lessons now encoded in the spec: `fit()` fits ~150 bars
  (deep zoom needs `setVisibleRange` over the full range), and a pending
  `_needsFit` from `setData` overrides a same-tick `setVisibleRange`
  (settle between them).

## D4. 2026-09-20 — Step 4: i18n string packs + `preset`

- **Scope: the chrome words, not the numbers.** Localized: empty state,
  stats-chip labels, measure readout, aria label. Numbers/dates already
  follow the viewer's locale via `Intl`; legend symbols (O/H/L/C/Vol) are
  language-neutral. Packs: `en` + `de` built in, hosts add their own via
  `WickChart.registerStrings(lang, pack)` (merged over English; unknown
  keys and unknown langs fall back to English). (Rejected: bundling more
  languages — bytes for guesses; a full i18n framework — zero-dependency
  is a core promise.)
- **`preset="minimal|pro"` is a starting point, never an override**:
  applies only to attributes the host did not set explicitly
  (`hasAttribute` guards). minimal hides legend/stats/volume; pro turns
  stats + inline volume on. Junk values restore the default chrome.
- **A constructor-ordering bug shipped for one commit-window and was
  caught by the browser layer, not the units**: `_nodata.textContent =
  _strings.noData` was placed with the DOM refs, before the defaults
  block assigned `_strings` — the constructor threw during upgrade and
  the element came up half-initialized. Duck-typed unit tests never run a
  constructor, so 605 units stayed green while every e2e failed. Lesson
  recorded: DOM-order-sensitive constructor changes need a browser
  smoke, which the per-step review loop provided.
- **Volume is an inline histogram in the main pane, not a pane** — the
  first e2e draft asserted `panes.length`; corrected to `_ind.volume`.
- **docs.html**: attribute-table rows + an `#i18n` section (pr21 gates
  every observed attribute into the docs). The phone-width gate caught
  the section's one-line `<pre>` snippet overflowing 412px — multi-lined.

## D5. 2026-09-20 — Step 5: the spread pane, as a core primitive + WickScript surface

- **Scoping: the roadmap item decomposed.** "A dedicated spread pane with
  its own axis — needs core pane support": pexpr panes already autoscale
  their own axis, and wickchart-compare already owns second-symbol data
  plumbing. The actual missing primitive was **cross-symbol WickScript**:
  no way for an expression to see another series. So: `setSeries(name,
  bars)` / `clearSeries(name)` on the chart, `alignSeries` in core
  (time-aligned, NaN in gaps), and `<name>_open/_high/_low/_close/
  _volume` variables in expressions — `pexpr:{close - eth_close}` IS the
  spread pane. (Rejected: a `formula="BTC/ETH"` attribute — a second
  parser and data-fetch contract in core for what WickScript + one
  method already express; rejected also: object member access in the
  script grammar — `eth.close` would grow the tokenizer for zero new
  power over `eth_close`.)
- **Aux rides the existing params channel** (`anchor` set the precedent)
  as an inline property read, not a helper method — seven test files
  borrow `_indicatorSeries` onto duck-typed stubs, and a new method call
  inside it broke 7 of them before the fix (the D1 lesson, now twice
  learned: no new seams inside borrowed methods).
- **Series names lowercase + underscore into variable prefixes**
  (`'BTC-USDT'` → `btc_usdt_close`) — case-sensitivity bit once in
  testing; the rule is now one sentence in the code comment.
- **Plugin note:** wickchart-compare can now feed `setSeries` to mount
  true spread panes instead of rebased overlay lines — that upgrade is
  the plugin's to make (its package, its budget); documented here as the
  follow-up.

## D6. 2026-09-20 — Step 6: columnar typed-array store — DEFERRED, on measurement

- **The decision: do not convert the main-thread `_data` store to typed
  arrays now.** The roadmap listed it as an M under "engineering &
  scale, continuous" — a standing option, not a commitment — and the
  evidence says the scale problem it targets is already solved where it
  exists:
  - **Render is O(pixel columns), not O(bars).** Browser-measured on this
    branch (Edge, 1280×800): default-view render 4.8ms at **1M bars**;
    full-zoom worst case 34.6ms at 1M — versus 35.5ms at 100k. The cost
    is flat in store size; the 1M full-zoom number is one O(n) min/max
    scan + column build, not object-field overhead.
  - **The scan columnar would optimize is 10.5ms per million bars**
    (full-store close read) — paid only on full-zoom renders. Typical
    views never scan the store.
  - **The heavy compute already runs columnar off-thread**: the worker
    path (PR #64) packs the dataset into transferable Float64Arrays once
    per epoch; indicators over 1M-bar histories never touch the
    main-thread store shape.
  - **`setData` ingestion (142ms @ 1M) is normalization + sort + dedupe**
    — "convert once" at ingestion pays the same cost in a different
    shape; no win there either.
- **The cost side is the real argument:** every `d[i].field` reader in
  the render path, alerts, stats, annotations, report and the data
  window changes; the public `chart.data` getter is pinned to `Bar[]` by
  plugins (tape, compare, navigator, paper) and the e2e suite, so a
  columnar store forces a permanent dual representation or lazy
  materialization churn. That is a focused, separately-reviewed refactor
  for a GC-pressure win — justified only when a profiler says so.
- **Reopen trigger:** a real workload where scan/GC time shows up in a
  profile (e.g. continuous full-history re-scans at ≥5M bars, or
  sub-16ms budgets on low-end mobile at full zoom). Until then the item
  is marked deferred in ROADMAP.md with this entry as the reasoning.
